Orchestration/End-to-end exampleIn development

End-to-end example

This page builds one environment from start to finish, first on a workstation and then in GitHub Actions: a dev environment whose single reconcile builds a container image, applies an OpenTofu configuration, and publishes Kubernetes manifests that consume both the image digest and the OpenTofu output, and a preview environment for every pull request that is removed when the pull request closes or expires. The same project, the same commands, and the same Git state serve both: a job in CI differs from a run on your laptop only in the credentials it holds. GitLab pipelines arrive with the CI adapters (M8); this page uses GitHub Actions, and every step is an ordinary nyl invocation that any CI system can run.

Where the listings come from

OpenTofu and Docker were not available where this page was written, so every console listing comes from a test build of Nyl (test-clock, test-kinds) that runs the project below with fake image and OpenTofu kinds and the built-in KubernetesPublication. The image reference and the database host are therefore the fakes’ (a digest derived from the unit’s execution key, not one a registry returned), and times come from the test clock. The nyl attest listings come from the same build reading a small local stand-in for the Argo CD API. Per-unit progress lines on stderr are left out, and paths are shortened to /tmp/shop. Everything else is Nyl’s own output. The same project runs with real OpenTofu, Docker Buildx, and a registry in the reference scenarios’ second tier on every change.

The project

Section titled “The project”

The project is nyl/tests/scenarios/examples/end-to-end/project in the Nyl repository, which CI runs end to end. Besides the application it has two directories: infra/database, an OpenTofu configuration, and services/web, a Dockerfile.

Add .nyl/ to .gitignore: Nyl caches under it, and a build that publishes refuses a worktree with untracked files it cannot attribute to a commit.

nyl/platform.yaml declares where things are published and which environment runs. The dev DeploymentTarget publishes the web Release with an image digest and a database host that come from units:

nyl/units.yaml declares the three units. The publication depends on the other two through the target’s fromUnit bindings, so nothing says so twice:

The OpenTofu unit’s root module declares backend "local" {} and an output connection, the image unit builds services/web, and the publication’s observe: {} is what lets nyl attest and nyl observe read Argo CD later (see Observing Argo CD). A local OpenTofu backend suits a workstation; CI needs a remote one.

nyl/preview.yaml is what makes every pull request an environment of its own. Each instance publishes its own tree to the previews branch behind one shared catalog Application, gets its own database and image, and expires after seven days of inactivity:

The ApplicationGroup in nyl/web.yaml names its Applications and AppProject after the target, so no two targets generate the same Argo CD names (nyl validate rejects the project otherwise), and it declares its labels in block style because its spec uses template syntax. Its namespace policy sets both prunePolicy and deletePolicy to Automatic: Argo CD holds an Application’s deletion while a Namespace it would delete is marked Prune=confirm or Delete=confirm, and either default (Confirm) would stall a teardown:

The Release in applications/web/release.yaml is a plain Deployment whose image is {{ inputs.image }} and whose DATABASE_HOST is {{ inputs.databaseHost }}. Nothing in it knows about orchestration.

Apply the catalogs once

Section titled “Apply the catalogs once”

Argo CD runs what the branches contain once it manages their catalogs. Apply each catalog Application once, by an operator, and Argo CD manages it from then on: dev/_nyl/catalog/application.argoproj.io/argocd/dev-catalog.yaml from the deploy branch, and _nyl/shared/previews/catalog.yaml from the previews branch once the first preview has published it. See Kubernetes GitOps for what the catalog contains.

Run it in CI

Section titled “Run it in CI”

Every job below runs the commands you ran locally from a fresh checkout. What differs is who may push and which credentials the job holds. Nothing else changes what Nyl renders or runs: it does not read the process environment beyond the variables a unit admits (CI run metadata such as GITHUB_RUN_ID only annotates what it records), the kube context, or files outside the repository.

Reconcile on main

Section titled “Reconcile on main”

The job runs the command from your terminal. It exits 0 when every unit is current, 2 when something waits, 3 when a unit failed, and 4 when one is uncertain (see nyl reconcile); the pipeline fails on anything but 0. --wait-lease makes it queue behind a run that holds the environment instead of exiting 2.

A workflow in CI cannot keep OpenTofu’s state in a local file: a runner is discarded after the job. Declare a remote backend on the unit and in the root module, and admit its credentials:

with terraform { backend "s3" {} } in infra/database/main.tf. See Terraform and OpenTofu.

Attest and observe

Section titled “Attest and observe”

Publishing is a receipt: the tree is on the branch. Whether Argo CD took it and its Applications are healthy is a separate fact only Argo CD knows. A job that holds the Argo CD read credential records it with nyl attest, and records the live values a unit declares (a load balancer’s address, say) with nyl observe:

With the Kubernetes API access, the job writes the kubeconfig whose context is the Cluster’s live.context (dev-admin) and admits it as KUBECONFIG; with the API server access, it sets ARGOCD_AUTH_TOKEN as above:

Before Argo CD has the catalog Application, an attestation cannot say anything, and it says so instead of failing:

Once Argo CD runs the publication and reports it healthy, the attestations pass. They record that each Application runs the tree the unit published, and that it is healthy:

A degraded Application fails healthy (exit 3) and keeps accepted. An Argo CD that cannot be read is never recorded as a failure: with the API server, a rejected token is reported as expired or invalid, and the unit is unknown (exit 2) until the credential is fixed.

The example declares no observed values, so there is nothing for nyl observe to read:

With them, as in Observed values, the same job keeps them current and the next reconcile resolves their consumers from the record. A unit that should run only against healthy workloads depends on the attestation (dependsOn: [{unit: kubernetes, attestations: [healthy]}]) and runs in the next reconcile without publishing again.

A preview for every pull request

Section titled “A preview for every pull request”

The checkout is of the pull request’s head commit. The instance records the commit it ran from, and the close job below fetches that commit from the repository after the branch is gone; GitHub keeps the head under refs/pull/<n>/head, but not the synthetic merge commit that a plain checkout of a pull_request event takes, so a preview job that ran from the merge commit could not be removed later without --source. --source-ref records that head ref next to the commit, for a host that refuses to serve a commit by its id: the close job then fetches the ref by name and looks for the recorded commit in it, never at the ref’s tip (see the pull request closed job). A local run of the same command just leaves the flag out and keeps what CI recorded.

The first run creates the instance, pr-1 here, in the shared nyl/previews ref: the template’s name, its parameters, the pull request’s commit as its source, and an expiry of seven days from now. Every later push extends the expiry and executes only what the push changed:

A second pull request gets its own instance, database, image, and tree. Both share one state ref and one deploy branch, and nyl get environments lists them with their expiry:

Each instance’s tree is an ordinary tree beneath its own prefix of the previews branch, with the catalog directory of its Applications. Beside them, _nyl/shared/previews/ holds the one shared catalog Application that manages them all, created by the first publication:

The shared catalog Application is a manifest like any other; an operator applies it once:

Close the pull request, and its job removes the preview. The job runs at the default branch, because the pull request’s own branch may be gone after the squash-merge. It needs no keep ref and no override: Nyl renders the units from the instance’s recorded source commit, the pull request’s last head, which a checkout of the default branch does not have, so Nyl fetches it by its id from the repository’s origin. GitHub keeps refs/pull/<n>/head after the branch is deleted, also after a squash merge, so the commit is still there (GitLab keeps refs/merge-requests/<n>/head):

The job reads the listing and removes only an instance that is in it, so a pull request that never had a preview skips the removal, while a listing that fails (an exit other than 0) fails the job instead of passing as “no preview”. The removal is teardown --all and then state delete: the publication removes its Applications from the catalog first and waits two minutes (the template’s delay) for Argo CD, then its files. The database is destroyed, the image unit is released (a registry image is never deleted), the instance’s state is removed, and the other preview is untouched:

If the recorded commit cannot be fetched

Section titled “If the recorded commit cannot be fetched”

The fetch needs a host that keeps the commit reachable and a job that may read it. Without that, the removal fails before it changes anything and names the way forward. This listing comes from a run in which nothing kept the commit after its branch was deleted (the lines about the units that wait for kubernetes are left out):

The fallback is --source <default-branch>, which takes the units’ source files from that branch instead of the recorded commit. Nyl warns (NYL-SOURCE-OVERRIDE, once per unit) and records the substitution in the transition commit:

The override is safe when the default branch’s configuration for those units can still destroy what the instance recorded: the same providers and backend, no unit configuration removed since, and every rename covered by a moved block. A squash merge of the pull request itself is the best case, because the default branch then holds exactly the configuration the preview ran. A pull request closed without merging, or one that changed the units long before it closed, is the worst: the teardown can fail at the unit or destroy something other than what the preview created, so read the warning before relying on it.

Scheduled maintenance

Section titled “Scheduled maintenance”

Nyl has no daemon, so expiry is work that people’s commands do. Previews whose pull requests were abandoned, or whose close job failed, are removed by a scheduled job that runs the same fleet reconcile for every instance of the template. It maintains the live instances at their own recorded commits without extending any, and removes the expired ones (allowTeardown: true lets it tear them down):

More than seven days after pr-2’s last push, the fleet job removes it and exits 0. An instance whose lease another run holds is reported as busy; a later run removes it:

The unit’s NYL-UNIT-RELEASED warning is the image: Nyl cannot delete a registry image, so it stays and its unit leaves state.

The writer renders the unit’s whole target, so it needs a live instance (or a declared environment) whose references resolve. It compares the branch’s manifest with the one the instance renders. --diff shows what would change and --push publishes it, only from a committed source:

Publications of the instances never overwrite the shared manifest, so pull requests on different Nyl versions do not fight over it; one that renders another manifest warns with NYL-KUBERNETES-SHARED-CATALOG-DIFFERS and reports differs in the tree artifact (nyl get artifact kubernetes/tree -e pr-2 --pointer /sharedCatalog/result, which prints current here). See One catalog for every instance.

Keep refs, for previews that outlive their branches

Section titled “Keep refs, for previews that outlive their branches”

The close job covers a preview that is removed when its pull request closes. A preview can also expire, through the scheduled job above, long after its branch is gone: an abandoned pull request, or a close job that failed. The scheduled job fetches the recorded commit by its id as well, so on GitHub and GitLab it needs no keep ref either. Set keepSource: true on the template for a host without pull request refs, or one that may prune that history before a preview expires. Every command that records an instance’s source commit then first pushes a ref of its own, refs/nyl-keep/<keepId>/<commit>, to the source repository, so the commit stays fetchable until the instance’s state is deleted.

keepSource: true needs a token that can push refs/nyl-keep/*

nyl reconcile --template and nyl state init --template refuse (NYL-INSTANCE-KEEP-FAILED, exit 1, nothing written) when the source repository refuses the ref. GitHub’s default read-only GITHUB_TOKEN, and the token of a pull request from a fork, cannot push it. The workflows above ask for contents: write because they push state and the deploy branch, and skip fork pull requests for the same reason. Either give such a job a token that may push the ref, or leave keepSource off and rely on the close job (or tear instances down with --source <revision>). See Source keep refs.
