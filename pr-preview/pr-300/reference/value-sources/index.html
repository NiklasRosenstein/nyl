Reference/Value sources

Value sources

A value source says where a value comes from instead of writing it inline: a file of this repository, a locked Git file, publication state, another unit’s receipt, or a promotion record. This page lists every source Nyl accepts, where each is valid, when it resolves, and what happens when it finds no value. The guides explain the workflows: Release inputs for target bindings, and References between units for unit specs.

Unit fields read the environment’s values with fromValues. A HelmChart reads its values from files and Release inputs with valuesFrom, and two of its fields from Release inputs with fromInput. A typed source clause for EnvironmentTemplate values is being added; until then, those values take literals and Jinja.

How resolution works

Section titled “How resolution works”

Render time and execution time

Section titled “Render time and execution time”

Nyl resolves a source at one of two moments:

  • Render time. The value comes from the declaration and the files Nyl reads while it renders: the Git worktree, a locked Git commit, or the target’s publication branch. Every command that renders the same document reads the same value, whether nyl render, render-tree, publish-tree, or a publication unit in nyl reconcile.
  • Execution time. The value comes from orchestration state: another unit’s current receipt, or a promotion record. Only orchestration resolves it, when a run resolves the unit, so it can change between runs without a commit. A source whose value does not exist yet blocks its unit, which waits instead of failing. Ordinary rendering rejects execution-time sources.

Reference objects

Section titled “Reference objects”

A source is written as an object with exactly one field, the source’s name, such as {fromUnit: {unit: database, output: host}}. It replaces the whole value it stands for:

  • An object whose only field is a source name is a reference, wherever the source is accepted.
  • An object that has a source name next to other fields is an error, because the reference would replace them.
  • Every other object is data, and so is a source name in a place that does not accept it.

Jinja

Section titled “Jinja”

Jinja in Nyl documents is for string interpolation, such as 'pr-{{ environment.name }}'. Templating that decides a value’s shape or type, such as {{ x | tojson }} or {% if %} around fields, makes the document invalid YAML before it renders and hides type errors until execution. Use it only where no source fits.

Release-input bindings

Section titled “Release-input bindings”

A DeploymentTarget binds the inputs a Release declares in spec.releaseInputs.<group>/<release>.<input>. Each binding sets exactly one source. See Release inputs for the workflow.

SourceResolvesReads
valuerender timeAn inline literal, never templated.
fromFilerender timepath, a YAML or JSON file of this repository under the local path rule, and pointer inside it.
fromGitrender timeA file of a Git repository at a locked commit, with repositoryRef or repository, revision, path, and pointer.
fromPublicationrender timeA state file in the target’s own publication branch: path relative to its path prefix, pointer, and optionally carryFileFromWorktree.
fromUnitexecution timeA unit’s output, artifact, or observed value; the fields are those of unit references. Only a target that a KubernetesPublication names resolves it.
fromPromotionexecution timeA value recorded through a PromotionPath: value and optionally path.

pointer is a JSON Pointer, such as /web/tier; empty or omitted selects the whole document.

Missing values. The effective value is the binding’s, otherwise the Release’s declared default. A fromFile file that does not exist, or a fromPublication branch or file that does not exist yet, leaves the input unbound, so the default applies. A pointer that selects nothing in a file that exists is an error. A required input without a value is an error that names the input and its description.

Types. Every value is checked against the input’s declared type and enum; null satisfies no type.

Errors. Nyl checks every binding of a target before rendering any Release and reports all problems together: unknown Releases or inputs, missing required values, and type mismatches.

Unit references

Section titled “Unit references”

Unit specs accept fromUnit and fromPromotion reference objects at any depth of their free-form maps, such as a Command’s values or a Terraform unit’s variables. Both resolve at execution time. See References between units for the workflow.

fromUnit takes:

FieldMeaning
unitThe producing unit.
output, artifact, observationExactly one: a declared output, a published artifact, or a declared observed value.
pointerA JSON Pointer inside the value.
environmentThe producer’s environment, for a cross-environment reference.
kindThe expected artifact kind.
evidence, attestationsWhat the producer must prove beyond a current receipt; see Requiring attestations.

fromPromotion takes value, the promoted value’s name, and optionally path, the PromotionPath it must come from. See Promotion for which record a binding reads.

Missing values. A unit document declares no defaults. A producer without a current receipt, an attestation that has not passed, or a promotion without a record blocks the consumer, which keeps its previous resolution and runs in a later run or wave. A reference that resolves to no value is an error.

Types. A referenced output has the type its producer declares, and a value bound to a Release input is checked against the input’s declared type before anything is published. A sensitive output cannot be referenced.

Errors. Each reference is a dependency on its producer. A cycle fails with NYL-DEPENDENCY-CYCLE, a unit the environment does not select with NYL-DEPENDENCY-UNKNOWN, and an undeclared attestation with NYL-ATTESTATION-UNDECLARED. nyl validate checks references without state.

Unit fields: fromValues

Section titled “Unit fields: fromValues”

A few fields of a unit spec read their value from the environment’s values instead of writing it inline, so one unit document serves environments that need different values without structural Jinja:

Where it is valid. Only the fields that declare it, and only in unit documents, including the inline target of a KubernetesPublication. A declared DeploymentTarget is not a unit document: its fromUnit bindings take a literal environment, and a fromValues there fails with where it works.

FieldUnits
spec.approval, spec.timeoutEvery kind.
spec.target, spec.teardownWaitKubernetesPublication.
environment of a fromUnit referenceEvery fromUnit in the spec, at any depth, such as in variables, values, or an inline target’s bindings.

The clause replaces the whole field. Every other place treats an object whose only field is fromValues as an error, never as data, and so does a clause in a document that is not a unit. The list grows only when a project still needs structural Jinja for a field.

When it resolves. At render time, when an environment’s units render: in nyl plan, nyl reconcile, nyl validate, nyl build -e, and every other command that renders units. pointer is a JSON Pointer into the environment’s effective values: an Environment’s values over its groups’ values, or an EnvironmentTemplate instance’s values. Those values are already rendered, so the value the clause reads is used as it is and never templated again. A fromValues inside fromUnit.environment resolves first, so the reference names its environment before the run resolves the reference itself at execution time. A direct nyl build without -e has no environment, so a unit with a clause needs -e.

Missing values. When nothing is at pointer, or the value there is null:

  • default applies. It must not be null.
  • With optional: true the field is removed, so the spec is the same as one that omits the field.
  • Otherwise it is an error.

default and optional are exclusive.

Types. The resolved value is checked exactly as the same literal would be, by the unit’s kind. A field filled from values renders the same spec as the literal, so its unit’s execution key is the same too: replacing Jinja with fromValues re-runs nothing.

Errors. A clause that cannot resolve fails the unit’s render with NYL-UNIT-INVALID. A missing required value names the environment, the keys that exist where the pointer stops matching, and the nearest one:

nyl validate renders every unit for every Environment that selects it, and for sample instances of every EnvironmentTemplate, so a pointer that one environment lacks fails before any run or instance exists.

HelmChart values: valuesFrom

Section titled “HelmChart values: valuesFrom”

A HelmChart can read its chart values from values files of this repository and from object Release inputs, merged in order, before its inline values:

Each entry sets exactly one source, and optionally pointer and key:

FieldMeaning
fileA YAML file holding one mapping, read without templating. The path rules are those of Cluster and DeploymentTarget valuesFrom: relative to the directory of the file that declares the HelmChart, / for the Git worktree root, never outside the worktree or through a symbolic link, and only a Git-visible file outside the project’s .nyl/cache. In a remote ApplicationGroup source, / is the root of its checkout.
inputA Release input of type object that the Release of this bundle declares. Its value is the target’s binding, or the declared default.
pointerA JSON Pointer that selects a value inside the file or input; the whole value when omitted.
keyMount the selected value under this key. Without key, the selected value must be a mapping, merged at the values root.

Where it is valid. In a HelmChart in a file of a Release bundle: the Release entry file or a file its spec.include selects, also without a Release for file entries. An input entry needs a Release that declares the input. A HelmChart that rendering generates, such as one a chart outputs, cannot use valuesFrom.

When it resolves. At render time, when Nyl loads the bundle’s files and before it renders the chart. Entries merge in order and the inline values merge last: maps merge key by key, and every other value, lists included, replaces. That is Helm’s own rule for several -f files.

The values are data. The merged values go to Helm as they are. Nyl never reads source clauses in them, before or after the merge, so an object such as {fromInput: …} inside values or a values file reaches the chart unchanged.

Missing values. There are no defaults: a missing file, a pointer that selects nothing, and an input the Release does not declare are errors. An optional input’s declared default applies when the target binds none.

Types. An input entry reads only an input of type object. Without key, the value it contributes must be a mapping.

Caching. Each file is an input of the Release’s render, and of its target’s tree, like an included file, and the merged values are part of the Helm render cache key, so changing a file or an input renders the chart again.

Errors. Each error names the HelmChart, its file, and the entry:

HelmChart fields: fromInput

Section titled “HelmChart fields: fromInput”

spec.includeCrds and spec.lookup of a HelmChart read a boolean Release input with {fromInput: {name, pointer?}}, so one Release bundle serves targets that need different settings:

Where it is valid. Only on these two fields, in a HelmChart in a file of a Release bundle whose Release declares the input. Every other place in a Nyl resource of the bundle treats an object whose only field is fromInput as an error; values, valuesFrom data, and a Component’s spec are chart data and are never checked.

When it resolves. At render time, when Nyl loads the bundle’s files: before anything reads the HelmChart, so lookup read from an input decides the cache and the lookup scope exactly as a literal would.

Missing values. The clause has no default: the input’s declared default applies when the target binds none. A pointer that selects nothing, and a null value, are errors.

Types. The value must be a boolean.

Errors. An input the Release does not declare, an input read outside a Release that declares inputs, and a value that is not a boolean fail the render with a message that names the HelmChart, its file, and the field.
