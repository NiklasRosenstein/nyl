Orchestration/Using EnvironmentTemplateIn development

Using EnvironmentTemplate

See the EnvironmentTemplate resource reference for the API, example, and field definitions.

An EnvironmentTemplate describes what a preview environment looks like, such as one environment per pull request. Source holds the template; each instance is created from it with parameters and exists only in state, in the state.yaml that nyl state init --template writes. Afterwards an instance behaves like a declared Environment for every command: plan, reconcile, status, get, attest, observe, teardown, state delete, and build.

Creating and updating an instance

Section titled “Creating and updating an instance”

state init writes the instance’s record without reconciling it; reconcile --template is what a pull request job runs: it creates or updates the instance from its own checkout and then reconciles it. Both record the template name, the bound parameters (defaults included), the entry checkout’s commit as the instance’s source, and an expiresAt of now plus ttl. Run again, they update the parameters. --param name=value parses the value as YAML and checks it against the declaration, so --param pr=123 is an integer. A parameter without a default is required.

Parameters are stored in plain text in the instance’s state.yaml, which anyone who can read the state ref can read, so never pass a secret as a parameter; give units secrets through their env.

The name must not belong to a declared Environment or to an instance of another template (NYL-INSTANCE-NAME-TAKEN), because leases, run refs, and state directories are named after it. A deleted instance refuses with NYL-STATE-DELETED until nyl state init --fresh starts it over.

Every later command names the instance with -e:

An instance is found only while its template exists at the entry checkout: a checkout that no longer declares the template reports NYL-INSTANCE-TEMPLATE-UNKNOWN. Renaming a template, or changing where its state puts instances, goes through nyl state move --template.

A plain reconcile -e pr-123 from any checkout renders the instance at the source commit its record names, not at the checkout, and records which commit it used; only reconcile --template, entered from the pull request’s own checkout, moves the recorded commit. get environments lists the declared environments and the live instances with their expiry, marking an expired one.

What renders with the parameters

Section titled “What renders with the parameters”

Every string of values, source, and protectedRefs that contains template syntax renders once, when an instance is created or loaded, with params and environment.name. A unit then sees the rendered values, so a values.target object that declares a publication’s inline target can name its prefix after the instance, and a unit places it with target: {{ values.target | tojson }}. A document that is not YAML before rendering needs a block-style envelope; see units.

state is different: it locates the state.yaml that holds the parameters, so it renders with environment.name alone. With path: '{{ environment.name }}' every instance of the template, and every declared environment that names the same refs, shares one ref and keeps its own directory, which also lets Nyl list the instances by listing the ref. A template whose refs or repository depend on the name works for every command that names the instance, but its instances are not listed.

Deletion policy and teardown

Section titled “Deletion policy and teardown”

deletionPolicy: Teardown overrides every unit’s own policy, an explicit Retain included, for units whose kind supports teardown. Units of other kinds, such as OciImage, are left in place and dropped from state when the instance is removed. allowTeardown: true lets a reconcile tear down a unit that left the template or its selection without --allow-teardown, because nobody is there to pass it for a preview.

Remove an instance with nyl state delete -e pr-123 --teardown: it tears down every unit, dependents first, and removes the instance’s files from the shared ref, leaving only the deleted marker in its state.yaml. A preview’s pull request closed job runs it, see the pull request closed job; see also Deletion.

The pull request closed job

Section titled “The pull request closed job”

Tear a preview down when its pull request closes. Two jobs share one concurrency group per pull request: the preview job creates and updates the instance, and the closed job removes it.

The closed job reads the listing and removes only an instance that is in it, so a pull request that never had a preview passes, while a failing listing fails the job. It checks out the default branch and removes the instance at the commit its record names, with no override.

The preview job must check out the pull request’s head, as above. On pull_request events actions/checkout checks out refs/pull/<n>/merge by default, a synthetic merge commit, and the instance would record that commit. GitHub does not keep it fetchable once the pull request closes, so the closed job could not fetch it and would fail with NYL-SOURCE-UNAVAILABLE. The head commit is the one refs/pull/<n>/head keeps.

The default branch is enough for the closed job because a command that lacks the recorded commit fetches it by its id from the clone’s origin remote (see Source keep refs). GitHub keeps refs/pull/<n>/head, the pull request’s last head, after the branch is deleted and after a squash merge, so the commit is still there when the job runs; the instance’s record names that last head, because the preview job records each push’s commit. With persist-credentials: false the checkout holds no token, so the fetch authenticates as the project’s [[git.credentials]] say (token_env = "NYL_GIT_TOKEN" here), as the state pushes of the same job do. cancel-in-progress: false and the shared group matter: a closed job that overlapped a preview job could remove an instance the other job is still creating.

--source-ref is for hosts that refuse to serve a commit by its id. The preview job above passes --source-ref refs/pull/<n>/head, which records that ref in the instance’s state.yaml next to the commit. The closed job’s checkout of the default branch lacks the recorded commit, so it tries, in order, the retained worktree snapshots, the instance’s keep ref, the commit by its id from origin, and last the recorded ref by name; it then looks for the recorded commit in what the fetch brought, never at the ref’s tip, so a pull request head that moved on, or a ref the host has dropped, leaves the commit missing (NYL-SOURCE-UNAVAILABLE, as without the flag). It is a flag on the job, not a field of the template, so the template stays the same for a local nyl reconcile --template run, which just omits it; a run without the flag keeps the ref CI recorded. The ref is only checked for being a full name under refs/ (see nyl state init), and GitLab’s is refs/merge-requests/<n>/head.

The closed job is the recommended teardown; it needs no keep refs and no extra permissions. The fleet job fetches the same way, so on GitHub and GitLab an expired preview whose branch is gone is removed without keep refs too. Two situations need more:

  • The commit cannot be fetched, because the host keeps no pull request ref (a self-hosted Git server without one), the job’s token cannot read it, or the job runs with --local. The teardown fails before any effect, names the unit and the commit, and suggests --source. nyl state delete -e pr-123 --teardown --source main takes the units’ source files from the default branch instead, warns (NYL-SOURCE-OVERRIDE) about the substitution, and records it in the transition commit. It is safe when the default branch’s configuration for those units can still destroy what the instance recorded: the same providers and backend, no unit configuration removed since, and every rename covered by a moved block. A squash merge of the pull request itself is the best case, because the default branch then holds exactly the pull request’s configuration; a pull request that was closed unmerged, or that changed the units long before, is the worst. A mismatch makes the teardown fail at the unit, or destroy something else, so check the warning.
  • The host does not keep the commit: no pull request refs, or history it may prune before a preview expires. Set keepSource: true: Nyl then keeps each instance’s recorded commit with a keep ref of its own, which needs push access to refs/nyl-keep/*.

Validation

Section titled “Validation”

Which instances exist is state, which nyl validate does not read. It checks each template through sample instances, with parameters taken from enum values or generated by type, so a template whose instances would collide fails before any exists: two instances sharing a state location, publication prefixes that overlap, or generated Argo CD Application and AppProject names that match each other or another target’s. Every publication render of every environment also includes the inline targets of the instances state lists, so a collision with a real instance is found whichever command renders. Template the names with environment.name or target.metadata.name, for example applicationNameTemplate: '${ target.metadata.name }-${ release.metadata.name }'.

A direct nyl build --push refuses to publish a target an instance owns. If a template’s state cannot be read, its instances are unknown, so a teardown, an exec, or a run of a unit that claims native resources refuses with NYL-STATE-UNAVAILABLE instead of checking without them. A deleted instance’s name still answers the owner fence of the prefix it published, as an owner that no longer exists.

Expiry, limits, and the fleet

Section titled “Expiry, limits, and the fleet”

Nyl has no daemon, so expiry works through the commands people already run:

  • Activity extends. state init --template, the pull request job’s reconcile -e pr-123 --template preview --param pr=123, and every other reconcile -e pr-123 move expiresAt to now plus ttl when they start, whether or not the run succeeds, so a pull request that keeps pushing keeps its preview even while the preview fails. plan, status, get, and teardown never extend it, and reconcile -e pr-123 --no-extend is maintenance that does not.
  • Expired instances are removed by the next reconcile that reaches them: a plain or --no-extend reconcile -e pr-123, or the scheduled reconcile --template preview, which maintains the live instances at their own recorded commits, never extends any, and removes the expired. Removal is teardown --all and then state delete, so nothing is deleted while a unit still has resources. allowTeardown: true authorizes the teardown; without it, or --allow-teardown, the run records the units as pending teardown and exits 2. A removal that waits (a publication’s teardownWait, an approval, unmet readiness) or fails leaves the state and exits like the teardown does, and a later run continues it. --renew keeps an expired instance, as does the pull request job’s reconcile --template: updating an active pull request never removes its preview. A renewal also undoes a removal that was recorded as pending teardown and has not started, so a preview renewed after an unauthorized sweep is not left fenced; a teardown that already started continues, and the units are created again after it completes. If the fleet did remove a preview, its pull request’s next reconcile --template creates it again (a new instance, under maxInstances).
  • maxInstances counts the template’s instances, expired ones until they are removed, when one is created. At the limit state init --template and reconcile --template exit 2 (NYL-INSTANCE-LIMIT) and write nothing, naming the expired instances that could go: removing them is the scheduled job’s work, not a side effect of another pull request’s job. --make-room opts in: it removes the expired instances with the oldest expiry first, only as many as needed and never a live one, and then creates the instance; it skips an expired instance renewed meanwhile and goes on to the next, and too few expired instances, or removals that do not finish, still refuse. The removal of other previews is authorized by allowTeardown as the job’s own checkout declares it, and does not inherit its --source or --approve. Nyl counts by listing, so maxInstances needs state.path: '{{ environment.name }}' and refs and a repository that do not read the name (nyl validate rejects the template otherwise). Two jobs creating at once can exceed the limit by one.
  • The fleet job. A scheduled job runs nyl reconcile --template preview from the default branch. It needs the same preview credentials as the pull request jobs. An instance whose lease another run holds is reported as busy and does not fail the job, and a later run removes it if it is expired. Removing an expired instance renders nothing from source, so a pull request branch that is gone does not keep it alive; the teardown of a unit that needs its files fails when the recorded commit can be neither fetched from the clone’s origin remote nor kept by keepSource: true, until --source <revision> supplies them.

A removal waits for each publication’s teardownWait, and the default manual waits for a person to confirm with --confirm-removed. Until someone does, the preview is half torn down: every reconcile of it, a pull request job’s included, exits 2, and nothing recreates its workloads. A template whose previews should expire unattended sets observe or delay on its publications; state init --template warns (NYL-TEARDOWN-WAIT-MANUAL) about a manual wait and about every unmet teardown requirement of the units it can resolve before their producers ran, such as a catalog that does not prune (NYL-TEARDOWN-CATALOG-MANUAL-SYNC). plan shows the rest once the units resolve.

Source keep refs

Section titled “Source keep refs”

Teardown needs the instance’s source files, and a closed pull request’s branch may be gone. By default Nyl pushes nothing to the source repository: the instance is torn down by the pull request closed job, while its recorded commit is still reachable. A command that needs the recorded commit and finds that the clone lacks it fetches it by its exact id from the clone’s origin, with the credentials Nyl uses for the other Git fetches. GitHub keeps a pull request’s commits reachable through refs/pull/<n>/head and GitLab through refs/merge-requests/<n>/head, also after the branch is deleted or the pull request is squash-merged, so a closed job that checked out only the default branch still finds the commit. Nothing but the recorded id is requested from the clone’s origin remote; if the host refuses, the command reports the commit as missing, as --source <revision> expects. A run with --local fetches nothing. The fleet job fetches the same way. A template whose host keeps no pull request refs, or may prune the history before a preview expires, sets keepSource: true: each instance’s recorded source commit is then kept fetchable through a ref of its own in the source repository, refs/nyl-keep/<keepId>/<commit>, and state delete removes them.

keepSource: true needs push access to refs/nyl-keep/*

state init --template and reconcile --template create the ref before they record the commit, and refuse when the source repository refuses it (NYL-INSTANCE-KEEP-FAILED, exit 1, nothing written). A read-only token cannot push it: GitHub’s default permissions: contents: read, and the token of a pull request from a fork. Either give the preview job a token that may push refs/nyl-keep/*, or leave keepSource off and tear instances down in the pull request closed job (or with --source <revision>).

How it works: a new commit is kept before the record names it and the instance’s older refs are removed after the record is committed, so the recorded commit is never unkept and a refused write pushes nothing. <keepId> is minted when the instance first keeps a commit and recorded in its state.yaml, so it is unique across projects of one monorepo and survives moves of the state or the project and renames of the template; the refs do not depend on the state’s coordinationRefPrefix, and that namespace is reserved (NYL-STATE-REF-CONFLICT for a state ref inside it). A ref that does not name the commit its name says is not the instance’s, and state delete leaves it with a warning. Every command that needs the recorded commit fetches it from the ref when the clone lacks it. A run with --local pushes and fetches nothing.

One catalog for every instance

Section titled “One catalog for every instance”

By default each target generates a catalog Application of its own, which an operator applies once and which stays after the target is removed. Previews come and go, so give them one catalog instead, in the template’s inline target:

The shared catalog Application sources the branch root with the include pattern {_nyl/shared/previews/*.yaml,*/_nyl/catalog/*}: its own manifest, and the catalog directory of every instance. Each instance’s tree stays an ordinary tree in its own prefix, without a catalog Application. The manifest lives under the reserved prefix _nyl/shared/<name>/, with its own ownership index whose owner is catalog:<name>, so no instance writes outside its prefix.

  • The shared block carries the settings that catalogApplication would otherwise carry for the target’s own catalog (project, syncPolicy, applicationDeletionPolicy, selfPrunePolicy, labels, annotations), defaulting to the ArgoCDInstance’s catalogApplicationDefaults. Declaring both is invalid.

  • The first publication of an instance creates the manifest when the branch has none. An operator then applies the shared catalog Application once, from the published _nyl/shared/previews/catalog.yaml or from nyl build <unit> -e <instance> -- --shared-catalog, and it manages itself.

  • A publication never overwrites the manifest, so pull requests running different Nyl versions do not fight over it. Creating it is a compare-and-swap: a publication that loses the race reads the new head and leaves the winner’s manifest. It records the result in the PublishedTree artifact (nyl get artifact kubernetes/tree -e <instance>): sharedCatalog.result is created, current, or differs, and for differs it warns with NYL-KUBERNETES-SHARED-CATALOG-DIFFERS in the run, and in plan and status until the unit executes again. To replace the manifest, for example after a Nyl upgrade or a change of the shared block, run the build from the revision that should win, in the scheduled job on the default branch, after the fleet reconcile:

    The build renders the unit’s whole target, so it needs a live instance (or a declared environment) whose references resolve, and a committed source and a commit identity for --push. With no live instance nothing uses the catalog, and the first instance’s publication creates it.

  • Rename or decommission a catalog as a procedure: a branch carries one shared catalog, and a second _nyl/shared/<other>/ tree refuses every publication and build (NYL-KUBERNETES-SHARED-CATALOG-CONFLICT), because each self-managing catalog syncs every target’s catalog directory. Delete the old Argo CD Application with its resources kept (a non-cascading delete, so the previews’ Applications stay), remove _nyl/shared/<old>/ from the branch in one commit, and only then publish the new catalog. Deleting it with its resources would cascade through every preview.

  • Dedicate the branch to the one catalog and one project: its include pattern and sync are the same for everything on it. One shared Application is also one sync for every preview: a manifest Argo CD rejects blocks all of them, and the observe teardown wait fails closed for all of them.

  • Teardown readiness reads the shared Application the branch holds (at resolution and again when a teardown starts, never the instance’s own declaration; the reading is recorded but not part of the unit’s key, so a writer’s push does not re-execute any preview) for its syncPolicy and deletion policy: it must prune for an instance’s Applications to disappear. Until the manifest exists, the rows are not checked; a branch that cannot be read (including offline: resolution has no cached fallback) or a manifest that is no Application is a blocking row. A teardown whose catalog no longer prunes is held by the driver even when the instance’s stored settings said it did, so run the writer before instances expire. The NYL-KUBERNETES-SHARED-CATALOG-DIFFERS warning is what the unit’s last execution found and stays until it executes again; nyl build <unit> -e <env> -- --shared-catalog --diff shows the branch’s state now. An instance leaves nothing of its catalog behind, because the shared catalog prunes its objects; the catalog itself stays until it is decommissioned.

  • The targets that name one catalog publish to one repository and revision, describe it identically, and nothing else is published to that revision. nyl validate and every render check this and fail with NYL-KUBERNETES-SHARED-CATALOG-CONFLICT, naming the targets. A target prefix may not lie at, beneath, or around _nyl/shared.

  • The target’s own AppProjects keep anchoring the observe teardown wait (see Observing Argo CD), as for any target without a catalog Application; a target whose only project is default fails closed.

Reading declared environments

Section titled “Reading declared environments”

An instance’s units read units of a declared environment, such as dev’s network, with the cross-environment references that fromUnit and dependsOn define:

The instance’s unit waits, exit 2, until dev’s network has a current receipt, and a later run reads it; provenance records dev’s observed commit. Instances are consumers only: a reference or dependsOn entry that names an instance, from a declared environment or from another instance, fails with NYL-REFERENCE-INSTANCE-PRODUCER and the fix.

A declared unit that an instance reads is protected like one that a declared environment reads: tearing it down, nyl state delete --teardown of its environment, and its replacement refuse with NYL-TEARDOWN-HAS-DEPENDENTS, naming the instance’s units, until --allow-dependents, and so does dropping it from its environment’s source. The instance then fails its own next run with NYL-REFERENCE-INVALID, naming the unit its producer no longer selects, while dev and every other environment run on: a preview’s bad reference, including one that names an instance, stops that preview alone. An expired instance that is being removed does not hold its producers back.
