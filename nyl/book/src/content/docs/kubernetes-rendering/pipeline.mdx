title: 'Rendering Pipeline'
---

`nyl render`, `nyl diff`, `nyl apply`, and the rendered-tree commands share one
manifest generation pipeline, so a local render and a CI render of the same
declaration take [one path](/nyl/start/introduction/#one-declaration-one-path). Tree commands add target composition, policy,
layout, and whole-target caching after each Release bundle has passed through
that pipeline.

## Shared Pipeline Steps

import { Steps } from '@astrojs/starlight/components';

<Steps>

1. Load project configuration and, when requested, resolve the target and its Cluster.
2. Build the template context. Project secrets and admitted `NYL_*` environment variables enter it only with `--allow-secret-inputs`, for direct and tree commands alike.
3. Load the input manifest file and render Jinja templates.
4. Apply `--only-source-kind` filtering on top-level input resources (before expansion).
5. Expand resources recursively (`HelmChart`, `Component`, `RemoteManifest`, aliases) with `--max-depth`. Generated resources inherit the expanding resource's [Argo CD sync wave and phase](#argo-cd-sync-waves-and-phases).
6. Apply Kyverno policies (Global scope currently supported).
7. Deduplicate final manifests (last occurrence wins).
8. Take the Release's resources as its Argo CD Application deploys them
   ([below](#the-releases-application)).
9. Apply post-render kind filtering with `--only-kind` / `--exclude-kind`.

</Steps>

Bundle expansion and parsed Helm output are cached by their complete observed
inputs. `--refresh` bypasses cache reads and replaces successful entries;
`--no-cache` disables persistent reads and writes. `diff` and `apply` always
perform their live-cluster work even when desired-manifest rendering is reused.

## Argo CD sync waves and phases

A `HelmChart`, `Component`, or `RemoteManifest` is never applied itself; the
resources it generates are. When it declares an Argo CD sync wave or phase,
every generated resource that declares none of its own inherits it, so a
chart can be ordered as a whole:

```yaml
apiVersion: k8s.nyl/v1
kind: HelmChart
metadata:
  name: cert-manager
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  chart:
    repository: https://charts.jetstack.io
    name: cert-manager
```

- `argocd.argoproj.io/sync-wave` is copied to each generated resource without
  its own sync wave or a `helm.sh/hook-weight`, which Argo CD uses as the wave
  of a Helm hook.
- `argocd.argoproj.io/hook`, the phase, is copied to each generated resource
  without its own Argo CD hook or a `helm.sh/hook`. The expanding resource's
  `argocd.argoproj.io/hook-delete-policy` comes with it, so a resource never
  combines its own phase with another resource's deletion policy, and one that
  inherits a phase without a deletion policy keeps none.

Other annotations are not copied. Nested expansion inherits transitively: a
`HelmChart` that a Component's chart renders passes on the wave it inherited.
Every command renders the same annotations, from `render` to `publish-tree`.

### Applying waves and hooks

The annotations only take effect when something syncs the resources. Argo CD does,
and so do the commands that apply a Release themselves: `nyl apply`, `nyl release
rollback`, and the [direct reconciler](/nyl/kubernetes-gitops/workflow/direct-reconciler/).
They share one implementation, so a Release is applied the same way by each:

- `PreSync` hooks run first and must finish (a Job completed, a Pod succeeded) before
  anything else is applied; then the `Sync` phase applies the ordinary resources and
  the `Sync` hooks wave by wave; then `PostSync` hooks run once the workloads are
  healthy. `SyncFail` hooks run only after a failure. `Skip` documents are never
  applied.
- Within a phase, resources and hooks run by sync wave, lowest first, then by kind,
  then by name. `helm.sh/hook-weight` is the wave of a document without its own sync
  wave.
- A hook is deleted before it is created again unless its delete policy says
  otherwise (`HookSucceeded` after a good sync, `HookFailed` after a failed one).
- Helm hooks map as Argo CD maps them: `pre-install` and `pre-upgrade` to `PreSync`,
  `post-install` and `post-upgrade` to `PostSync`; `crd-install` documents are
  ordinary resources; hooks with no sync phase (`test`, `pre-delete`, `post-delete`,
  `pre-rollback`, `post-rollback`) are left out with a warning.
- Hooks are not owned objects: they are not pruned, purged, or compared, and a hook
  that is gone is not drift.

A Release that declares no waves or hooks is applied in one step, as before. The
rules, the waits, the failure behavior, and where Nyl differs from Argo CD are in
[`nyl apply`](/nyl/reference/cli/apply/#hooks-and-sync-waves); `nyl diff` lists the
hooks that would run apart from the resource changes.

## Resource errors

Nyl's own resources (`HelmChart`, `Component`, `RemoteManifest`, `Release`,
and the Kubernetes GitOps resources) reject unknown fields and values of the
wrong type. The error names the source document, the resource kind, the path
of the offending field, and a hint for fixing it:

```console
$ nyl render chart.yaml --kube-version 1.28.0 --kube-api-versions v1
ERROR nyl: Render error:
Source: chart.yaml (document 1)
Resource: k8s.nyl/v1 HelmChart default/web (chart: web)
Caused by: Invalid HelmChart: Type mismatch at `spec.chart.version`: invalid type: sequence, expected a string
Hint: Check that the field value matches the expected type. For example, numbers should not be quoted, booleans should be true/false.
```

Failures are classified as an unknown field, a type mismatch, or a missing
required field; a missing field is reported at the path of the object that
lacks it.

## YAML Data Preservation

Nyl preserves manifest keys, values, and types when its YAML output is parsed
again. Comments, quoting style, and whitespace outside string values are not
preserved. Multiline manifest values use literal blocks when their contents can
be preserved safely; values requiring escaping use quoted strings. Long
single-line strings are not folded.

Quote strings that resemble YAML booleans, numbers, or null, such as `"no"`,
`"123"`, and `"null"`. Mapping keys are strings and retain their spelling.
Duplicate mapping keys are rejected. YAML aliases are expanded within parser
resource limits. Manifest streams apply complexity limits per document, so
combining many resources does not impose a fixed document-count ceiling. Empty
and null documents are omitted from manifest streams.

## Embedding JSON in templates

Templates print a list or mapping in Python-like syntax, such as
`{'enabled': true}`, which is not JSON. To embed a value as JSON, for example
in a ConfigMap or an annotation, serialize it with the `tojson` filter:

```yaml
data:
  config.json: '{{ values.config | tojson }}'
```

`tojson` escapes quotes, newlines, and backslashes as JSON requires, and writes
`<`, `>`, `&`, and `'` as `\u` escapes. That keeps the output valid JSON inside a
single-quoted YAML string. For readable output in a block scalar, indent the
serialized lines to the block's depth:

```yaml
data:
  config.json: |
    {{ values.config | tojson(indent=2) | indent(4) }}
```

Other values print as written in manifest templates, without JSON or HTML
escaping.

## The Release's Application

With `--target`, a Release that one of the target's enabled ApplicationGroups
renders is taken from the compiled target, the tree `render-tree` publishes. The
direct commands therefore work on exactly the resources its Argo CD Application
deploys:

- Resources without `metadata.namespace` keep none; the Application's
  destination namespace (the group's `destinationNamespace`, else the Release
  namespace) gives them one.
- The destination and `spec.additionalNamespaces` get managed Namespace objects
  by the group's `namespace` policy, unless `sharedNamespaces` gives a namespace
  to another owner or it is a Kubernetes bootstrap namespace such as `default`.
- Namespace scope rules and shared-namespace ownership across the target's
  Releases are checked as `render-tree` checks them.

Compiling the target renders its other Releases too; the render cache makes
repeated runs cheap. `--release-only` settles the Release alone instead: it
applies the same per-Release rules with its group's policy, but cannot see
conflicts with other Releases, such as a namespace two groups use without a
`sharedNamespaces` declaration. A Release with `--input`, `--inputs`, or
`--defaults-only`, outside every group of the target, or rendered without a
target is settled alone the same way, without a group's policy where it has
none.

## Namespaces in diff and apply

`render` leaves missing namespaces unset, as the published tree does. `diff` and `apply` fill them in for namespaced kinds,
as Argo CD does when it syncs:

1. the resource's own `metadata.namespace`;
2. the destination namespace of the Release's Application;
3. `--namespace`, for a file without a Release;
4. otherwise an error naming the resource.

The kube context's default namespace is never used, so the result depends only
on the declaration.

## Without GitOps configuration

`render`, `diff`, `apply`, `release`, and [`argocd`](/nyl/reference/cli/argocd/)
also work in a project that declares no DeploymentTarget, or that has no
`nyl.toml` or Git worktree, when `--context` names a kube context. That flag is
the explicit opt-in to a cluster the declaration does not describe:

- The Kubernetes version and API versions Helm renders with come from the live
  cluster instead of a Cluster resource; `--kube-version` and
  `--kube-api-versions` are rejected.
- There are no target or Cluster values and no ApplicationGroup bindings, so a
  Release is settled alone, as without a target.
- Namespaces follow the same rules as above: the context's default namespace is
  still never used.
- Nothing checks the context against a declared server, because there is none.

When the project declares DeploymentTargets, a target is always used, even with
`--context`; the flag then only selects how to reach its Cluster, and Nyl checks
that context against the Cluster's server. `render` with a target never
connects. Without `--target` or `--context` and without targets, `diff`,
`apply`, and `release` fail and name both flags.

`render-tree`, `diff-tree`, and `publish-tree` have no such mode, so nothing
read from a live cluster reaches a publication.

## Pruning and deletion

`apply` prunes resources the new revision no longer renders, and
`release delete` purges a release's resources, by the Argo CD sync options each
live resource carries:

| `argocd.argoproj.io/sync-options` | `apply` pruning | `release delete` |
| --- | --- | --- |
| `Prune=false` / `Delete=false` | kept and no longer tracked | kept |
| `Prune=confirm` / `Delete=confirm` | kept and still tracked, unless `--confirm-prune` | kept, unless `--confirm-delete` |
| neither | deleted | deleted |

Managed Namespaces carry `Prune=confirm` and `Delete=confirm` by default (the
group's `namespace.prunePolicy` and `deletePolicy`), because deleting a
Namespace deletes everything in it. `diff` lists kept resources separately and
accepts `--confirm-prune` to preview a confirmed apply.

## Command-Specific Behavior After Rendering

- `render`: outputs rendered YAML to stdout.
- `diff`: compares desired state with live cluster state and prints differences.
- `apply`: applies resources and manages release tracking/pruning.

## Source Filter vs Post-Render Filters

- `--only-source-kind` filters only top-level resources in the input file, before expansion.
- `--only-kind` / `--exclude-kind` filter the final rendered manifests, after expansion.
